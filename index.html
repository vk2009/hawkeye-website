02 — Motivation

Why This Project?

Driving Questions

"How can we create an app that can be used to make subjective calls in cricket, objective in non-professional games?"

"How can we use less cameras, preferably one, to make this program operational?"

I have played cricket for as long as I can remember. Cricket at the amateur level carries a frustration that professionals rarely have to endure: bad umpire decisions that stick.

At professional level, the Decision Review System (DRS) exists precisely to solve this problem. Hawkeye cameras, ball-tracking algorithms, and instant replays give both teams a mechanism to challenge incorrect calls. A clear LBW (leg-before-wicket which is a highly contentious decision) that was given not-out can be overturned in seconds using multiple cameras and sophisticated algorithms. But for the hundreds of thousands of players competing in club leagues and amateur games in the US and around the world, none of that technology exists.

I experienced this personally. In many crucial league matches, a clearly missing delivery was given LBW against our best batter, and it costs us games. On the flip side, LBW's that go on to clearly hit the stumps are rejected by the umpire, frustrating bowlers. There was no review to even see what the ball was doing.

As computer vision has become accessible and with the rise of AI, the possibility of creating a more inclusive and fairer cricket experience becomes a reality.

🏏

The Problem

Amateur leagues have no access to ball-tracking DRS. Incorrect LBW and catch decisions go unchallenged, unfairly altering match outcomes.

💡

The Need

A low-cost, single-camera solution that can be set up at any ground — no expensive hardware required.

🎯

The Goal

Reconstruct 3D ball trajectory from 2D footage, predict impact and pitch points, and render a visual review — accessible to every club.

This project sits at the intersection of two things I care deeply about: cricket and computer science. Building Hawkeye DRS from scratch — from the physics engine to the 3D visualisation — felt like the right way to spend a lot of time on serious work, because the outcome would be something genuinely useful to the sport.

03 — Process

How I Built It

The project unfolded across several distinct phases — each one revealing new challenges that required more research, and a revised approach. What started as a computer vision task quickly grew into a full pipeline spanning physics simulation, 3D rendering, and real-time tracking. In the end, I wasn't able to make a fully fleshed out product, but I am hoping to continue this project into the summer and the following years!

1

Research & Scoping

I started by learning about computer vision and consulting mentors like my father, who is an expert in Computer vision. The key challenge with a single camera is depth — without a second viewpoint, you cannot directly observe the Z-axis. Luckily, I have access to some code that does a similar task. Creating a prediction algorithm was also tricky as I was unsure how to approach it.

2

Simulation

I initially wrote a simulation script that used ideal physical principles of projectile motion to create a model for the ball's path. I first created a set of points created by a function that uses physics principles to create a set of points. Then I used these points to simulate the ball's trajectory with another predictive function. I polyfitted the points to form a smooth parabolic curve. This model was to first see what the idea would look like in practice. It also served as a template for the predictive algorithm that utilized the gap between balls and its trajectory to model a prediction.

3

Ball-Tracking

Tracking the ball across frames was a significant challenge, especially with the limited depth information from a single camera. I am yet to solidify this step as I have some code that tracks the ball's position across multiple frames, but no integration between the predictive algorithm and the tracking system.

4

Predictive Algorithm

With trajectory data in hand, I built a full cricket pitch scene in Blender and wrote blender_original.py to programmatically animate a ball object along the computed path. This script runs inside Blender's Python environment, reading trajectory output and driving the ball's keyframes. I iterated through multiple versions (hawkeye2.blend, hawkeye3.blend) to improve camera angle, lighting, and the clarity of the impact and prediction zones. Using the blender scene I created a fully predictive model that requires additional tuning.

5

Rendering & Output

The final pipeline renders a video showing the ball's actual tracked path and predicted continuation, with visual markers at the pitch point, impact point, and projected wicket contact. I rendered multiple simulation variants to validate the visualisation against known ball paths, checking that pitch point and impact markers were accurate to within acceptable margins.

04 — Product

The Final Product

The product is a functional ball-tracking and trajectory-visualisation pipeline that takes a single-camera video of a cricket delivery and produces a rendered animation showing the ball's path, pitch point, impact point, and predicted trajectory through the stumps. The system is designed to be accessible to amateur players and clubs, requiring only a standard video recording setup and a laptop for processing. It is not yet a polished app as we have to tune the prediction models, integrate videos, and do a lot more testing.

The system utilizes custom code for ball detection and tracking and Blender's Python API for rendering the visual output. The core innovation is the ability to predict the ball's path beyond the point of impact, allowing for an LBW decision review even when the ball is intercepted by the batter's pad or bat.

The output video shows the ball travelling from release to impact, with a pitch-point marker appearing where the ball first makes contact with the ground, an impact marker at the point it struck the batter's pad or bat, and — critically — a predicted trajectory line showing where the ball would have continued had it not been interrupted. This predicted path is compared against the wicket geometry to determine whether the delivery was hitting the stumps: the core of every LBW decision.

🎥

Any single-camera video of a delivery. Works with smartphone footage at 30fps or above.

📐
